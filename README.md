Задание 1. Проектирование архитектуры

Выделено 5 основных поддоменов с учетом 5 GO-разработчиков.

Поддомены:

1.1 Core-поддомен: Entertainment
Контексты:

- Контекст транзитных систем для расположения legacy-системы. Данный контекст предназначен для систем временного взаимодействия или миграций.
Сервисы: 
Old Monolith - legacy-система
Monolith Relational Database - реляционная база для монолитной системы

- Контекст обогащения. Контекст в котором располагаются сервисы метаинформации, каталог контента.
Сервисы:
Library - основной сервис для работы с каталогом.
Library NoSQL Database - база данных каталога. Выбрана schemaless база данных, так как система является агрегатором и неструктурированные данные могут оказаться предпочтительными при работе с разными источниками.
Meta - сервис метаинформации для контента
Metadata NoSQL Database - база данных метаинформации. Использована schemaless база данных, т.к. метаданные могут принимать разную форму и содержать разные колонки/типы данных.

- Контекст доступа к данным. Контекст реализует сервисы контроля за потреблением трафика и доступа согласно подписке
Сервисы:
Access Control/Deeplink - сервис контроля доступа к контенту согласно подписке, защита от шеринга и подпись URL адресов.
Access Control Immutable Database - иммутабельный журнал для ведения логов обращений и выдачи ссылок.


1.2 Поддомен: Инфраструктура
Контексты:
- External Communications Context. Контекст, в котором реализуются сервисы, связанные с коммуникациями с пользователем, внешними системами, единой точкой входа в инфраструктуру.
Сервисы:
Gateway - NGINX Gateway. Единая точка доступа к инфраструктуре, проксирует запросы на BFF для клиентов.
Mobile/WEB/TV-BFF - Backend-for-frontend для клиентских приложений. Логируют, агрегируют, валидируют, фильтруют данные, необходимые для пользовательской выдачи.
Notifications - сервис для коммуникации с клиентскими приложениями. Высылает сообщения по сокет-каналу, email-оповещения, смс.

- Partner Integration Context. Контекст, в котором реализуются сервисы интеграций с партнерами (лояльность, дополнительный контент)
Сервисы:
Content Integration Gateway - gateway для реализации интеграций с партнерами. Новый контент, программы лояльности.
RabbitMQ - брокер сообщения для рекомендательной системы. Атавизм legacy.

- Internal Communication Context. Контекст, в котором реализуются операции внутренних коммуникаций (kafka) и коммуникаций транзитных систем (ACL Layer).
Сервисы:
ACL - Anticorruption Layer - сервис созданный для бесшовной миграции с монолитной системы на микросервисы. Нивелирует разницу протоколов, формата данных между новой системой и legacy, выступая middleware.
Kafka - брокер сообщений для коммуникации компонентов системы


1.3 Поддомен: ROI & Money Flows
Контексты:
- Financial Operations Context. Контекст для реализации сервисов подписки и оплаты
Сервисы:
Earning - сервис для операций, связанных с извлечением прибыли, на текущий момент это подписки.
Earning Relational Database - реляционная база данных для сервиса Earning. Выбрана PostgreSQL из-за надежности и требований к ACID
Payment Gateway - сервис для инкапсуляции логики оплаты подписок
Payment Relational Database - база данных для платежного шлюза. PostgreSQL выбрана исходя из таких же предпоссылок, как у Earning: надежность, ACID

- Reward Context. Контекст для реализации сервиса вознаграждения пользователя
Сервисы:
Loyalty - сервис, инкапсулирующий работу программ лояльности
Loyalty Immutable Database - иммутабельная база данных EventStore. Иммутабельность выбрана для дополнительной гарантии истинности данных. Гарантии истинности данных нужны из-за связи бонусов с финансовым состоянием организации.

1.4 Поддомен: Business Intelligence
Контексты: 
- Planning & Evaluation Context: Контекст планирования и оценок. Для возможности анализа того, в правильном ли направлении движется бизнес и система, как проекция его части.
Сервисы:
Monitoring - сервис для сбора и визуализации метрик. Выбран стандартный opensource стек Grafana/Prometheus из-за широкого community, подтвержденной временем надежности и лицензии, позволяющей использовать инструменты в коммерческих продуктах.

- Troubleshooting Context - Контекст для сервисов логирования и поиска по логам. Необходим для отслеживания проблем в системе.
Сервисы:
Search - сервис для гибкого поиска информации в логах. Выбрано стандартной решение на базе ElasticSearch.

1.5 Поддомен: Security
Контексты:
- Authorization Context. Контекст для реализации сервисов SSO авторизации.
Сервисы:
Identity - для аутентификации и авторизации в системе выбрано opensource решение KeyCloak с базой данных PostgreSQL.

- Internal Control Context. Контекст для контроля действий при совершении критических операций внутри системы.
Сервисы:
Audit - сервис для внутреннего контроля действий внутри системы. 
Audit Immutable Database - база данных сервиса аудита. Данные аудита не могут быть удалены или изменены, поэтому выбран EventStore в роли неизменяемого хранилища.
